A2) WHAT IT IS  (one place; pitch phrasings live in D1)
-----------------------------------------------------------------
An event-first social platform. Instead of a follower graph, connections
form through shared real-world attendance: discover events near you,
commit to attend, connect with the people who were actually there.
  Problem it attacks: mainstream social optimizes engagement loops (feeds,
    likes, follows) that rarely become real relationships.
  The bet: make real-world attendance the trust signal.
  The loop: DISCOVER -> COMMIT -> SHOW UP -> CONNECT.
  For: attendees (meet people via shared interests), hosts (publish,
    track attendance, QR check-in), communities (trust over follower counts).
  Three promises -> features:
    RELEVANCE -> ranked discovery feed (B2).
    TRUST     -> connections anchored to a shared event (Connection.sharedEventId).
    ACTION    -> swipe-to-commit, reminders, tickets.

PART B — HOW IT WORKS  (subsystem walkthroughs)
#####################################################################
Format: FLOW · HARD PART · GOTCHA. Endpoints/models are in A5/A6, not repeated.

B1) AUTH & OTP
-----------------------------------------------------------------
Model: NextAuth v4, single Credentials provider, JWT strategy. No OAuth —
(email OR phone) + password, but the contact is OTP-verified before a
password exists.
SIGNUP FLOW (5 steps):
  1 send-otp: normalizeContact; EMAIL = generate 6-digit code, bcrypt-hash,
    store OtpToken (5-min expiry), send via Nodemailer; PHONE = Twilio Verify
    startVerification, store only a verificationSid. Guards: per-IP limit +
    30s per-contact cooldown.
  2 verify-otp: EMAIL bcrypt.compare; PHONE Twilio checkVerification. On
    success set verifiedAt, RETURN the OtpToken id. Attempt counter caps tries.
  3 register: reload OtpToken by id (must be verified/unexpired/unused),
    bcrypt-hash password, create User (profileComplete=false), mark OTP used;
    if ref present, complete the referral (B5).
  4 auto-login: signIn("credentials") -> authorize() issues the JWT.
  5 onboarding: PUT /api/users/me (profile) then PUT /api/users/me/location
    {profileComplete:true}; session.update refreshes the JWT claim -> /explore.
LOGIN: authorize() = normalizeContact -> per-IP limit (10/15min) ->
  findFirst(email OR phone) -> reject if missing/isDeactivated ->
  bcrypt.compare -> return {id,name,profileComplete,isDeactivated}.
TOKEN JOURNEY (authOptions callbacks): jwt() on sign-in copies claims [no DB];
  on every later call — including session.update() from the client — it
  RE-READS DB for profileComplete/isDeactivated [DB]; client-passed claim
  values are ignored (the DB is the only source of truth). session()
  projects claims onto session.user. So middleware validates with no DB hit;
  claim freshness depends on the last jwt re-read.
HARD PART: two OTP mechanisms behind one interface — email codes WE own
  (hash+store+compare); phone codes Twilio owns (we store only a sid). Route
  branches on whether a verificationSid exists.
GOTCHA: verify sets verifiedAt but the token isn't marked used until
  register/reset consumes it -> its id is a short-lived bearer credential,
  replayable in the 5-min window, and passed in the URL between steps.

B2) EVENT DISCOVERY & RANKING  (the feed)  ★
-----------------------------------------------------------------
FLOW: load user lat/lng+preferences -> fetch public events (where
  visibility="public", page size 50, ordered eventDate) -> if logged in,
  find which of those events the user's accepted connections attend -> score,
  sort desc, return.
SCORE (memorize weights):
  0.30 locationProximity  (Haversine, exp(-km/10))
  0.25 categoryMatch      (1 if event.category in prefs)
  0.15 timeProximity      ((7-daysUntil)/7, clamped)
  0.15 connectionsAttending (1 if a connection is going)
  0.10 popularity         (currentAttendees/maxAttendees)
  0.05 recency            (newer scores higher)
HARD PART: encodes the three promises — relevance (location+category),
  trust (connections), action (time urgency).
GOTCHA (real design flaw, great talking point): ranking runs AFTER
  pagination — it scores only the 50 earliest-by-date rows, so globally best
  matches never surface; and past events aren't filtered, so a past event's
  daysUntil clamps to 0 and gets the MAX time score. Fix: filter
  eventDate>=now and rank in SQL before paginating (scale path in C4).

B3) COMMIT TO EVENT & CAPACITY  (concurrency)  ★
-----------------------------------------------------------------
FLOW: load event; reject if paid (isFree=false -> 403); pre-check existing
  attendee -> "already-committed"; TRANSACTION { create EventAttendee;
  `UPDATE events SET current=current+1 WHERE id=? AND current<max`
  ($executeRaw); 0 rows -> throw EVENT_FULL, which rolls the insert back };
  EVENT_FULL->409, Prisma P2002 (same user twice) -> "already-committed"; if
  reminders enabled schedule 1-day/1-hour/10-min NotificationSchedule rows
  (idempotent via the unique key). Cancel = delete attendee + decrement with a
  >0 floor + delete that user's unsent reminders, in one transaction.
HARD PART: two users racing the last seat. The conditional UPDATE serialises
  them on the row lock, so the invariant lives in ONE statement;
  UNIQUE(eventId,userId) covers the same user twice. Lesson from v1
  (read-then-check inside a txn): "wrap in a transaction" != "serialise the
  invariant".
GOTCHA: capacity still relies on the denormalised counter (C1.5); a DB
  trigger or a COUNT(*) reconciliation job would make drift impossible.

B4) REALTIME CHAT  (Socket.io)
-----------------------------------------------------------------
FLOW (persistence via REST, delivery via socket): open thread -> GET history
  -> boot socket (fetch /api/socketio) + join(connectionId) -> send = POST
  (DB write) then server emitToRoom "message" -> both clients update -> read =
  PUT .../read flips readAt + emits "read" -> typing = client emits "typing"
  (1.5s debounce), relayed to the room. Rooms keyed by connectionId.
HARD PART: hosting a persistent socket in App Router — it can't, so
  pages/api/socketio.ts lazily boots Socket.io and stashes it on
  globalThis.io; API routes emit via lib/socketServer.ts. Single-node emits
  can silently no-op, so the sender re-fetches after a successful POST — the
  DB is the source of truth.
GOTCHA: (security — closed) the handshake is authenticated from the NextAuth
  cookie (lib/socketAuth.ts), `join` verifies connection membership, there is
  no client "message" relay, and typing carries the server-known userId; the
  read route is participant-gated and POST requires status=accepted. (scale)
  globalThis assumes one Node process -> breaks on serverless fan-out; needs a
  Redis adapter (C4).

B5) GROWTH LOOP  (contacts -> referral -> auto-connect)
-----------------------------------------------------------------
FLOW: import contacts (Contact Picker or manual) -> invite (referrals/share
  creates ContactInvitation + ReferralLink with a unique code, sends
  SMS/WhatsApp with /join?ref=CODE) -> invitee opens /join (GET referrals/:code
  tracks click) -> signs up with ?ref=CODE; ref threads verify->password->
  register body; on register the code resolves: invitation marked registered,
  an accepted Connection created, both users notified, stats incremented —
  all non-fatal.
HARD PART: threading the code through an OTP-gated multi-step signup so the
  auto-connect fires exactly once at account creation, and matching an invited
  phone to the new account.
GOTCHA: the old unauthenticated POST /api/referrals/:code (client-supplied
  newUserId, IDOR) was removed outright — the only completion path is inside
  register, keyed to the account being created; codes come from
  crypto.randomInt. Still open: contacts/sync deletes+recreates all imports
  each run (loses invite history) and auto-connects matched users without
  consent.

B6) TICKETS & QR VALIDATION
-----------------------------------------------------------------
FLOW: Ticket has a unique qrCode rendered with qrcode.react (tickets/me lists;
  tickets/:id/qr returns the value). Host "scanner" page POSTs to
  tickets/validate -> verify caller is host -> find ticket by qrCode+eventId
  -> 404 if none -> 409 if already validated -> set qrValidated + mark
  attendee "attended". Refund flips paymentStatus, removes attendee,
  decrements counter (<48h blocked).
HARD PART: authorization + idempotency at the door — only the host validates,
  and a QR must validate exactly once (unique qrCode + qrValidated flag;
  scoped by qrCode+eventId + host check).
GOTCHA: the "scanner" is manual paste, not a camera. Validation is a
  conditional updateMany (qrValidated=false) so a racing second scan gets 409;
  refund is one transaction, refuses already-scanned tickets and floors the
  counter. Refund issues NO real money (no processor wired) — it only flips
  status; payments were intentionally out of scope, so the ticketing/payment
  infra is half-built (no endpoint creates tickets).

B7) NOTIFICATIONS & DISPATCH
-----------------------------------------------------------------
FLOW: in-app Notification rows (list newest 50, mark/dismiss owner-checked,
  read-all). Reminders live as NotificationSchedule rows (B3). Cron dispatch
  every 5 min: in one transaction `updateManyAndReturn` claims every row with
  sendAt<=now and sentAt=null (a single UPDATE ... RETURNING), then createMany
  Notification rows from the claimed set; a failed fan-out rolls the claim
  back. Dual-auth (Bearer CRON_SECRET or NOTIFICATION_DISPATCH_SECRET); both
  checks guarded so an unset secret can't be bypassed.
GOTCHA: overlapping runs can no longer double-send and the backlog drains in
  one pass; scheduled email/push isn't wired (dispatch only makes in-app
  rows; the old no-op subscribe stub was removed).

#####################################################################

C1) DESIGN DECISIONS & TRADE-OFFS
-----------------------------------------------------------------
Template: "Chose X for [benefit]; cost is [downside]; revisit when [trigger]."
  1 MONOLITH — one deploy/language/types, no CORS; cost: coupling + realtime
    can't scale alone; extract the socket server first if needed.
  2 JWT SESSIONS — edge auth, zero DB hits; cost: no instant revocation
    (deactivation/reset don't kill live tokens); fix: short JWT + refresh.
  3 JWT CLAIMS (profileComplete,isDeactivated) — edge gating without a query;
    cost: staleness + the update-trigger trusts client values (bug, C2).
  4 NO ONLINE PAYMENTS — removes PCI + Stripe; cost: ticketing/refund
    half-built; fix: Stripe + webhooks, transactional refund.
  5 DENORMALIZED currentAttendees — O(1) capacity/popularity; cost: can drift/
    go negative; fix: atomic conditional UPDATE or a DB trigger.
  6 IN-MEMORY FEED SCORING — simple, fine now; cost: ranks only the page
    (B2 flaw); fix: SQL/PostGIS or a search engine.
  7 IN-MEMORY RATE LIMITER — zero-dep; cost: per-instance, serverless-
    ineffective; fix: Redis INCR+TTL.
  8 SOCKET.IO ON globalThis — only way in App Router; cost: single-process;
    fix: dedicated socket server + Redis adapter.
  9 PRISMA — shared types + migrations + txns; cost: leaky for geo; fix: raw
    SQL/PostGIS on the hot path.
  10 POSTGRES — relational integrity (unique attendee, cascades, txn
    capacity); document DB would fight all of it.
  11 TAILWIND + hand-rolled UI — fast; cost: design-system drift; fix: a
    shared Button/Input primitive (the never-used Button.tsx was deleted
    rather than left half-adopted).
  12 SUPABASE — managed PG+Storage+pooling; cost: some coupling (hardcoded
    storage host in next.config); fix: parameterize.
  WHY user1/user2 not a directed follow: the request is directional
    (preserve initiator for accept/notify); queries treat it undirected via
    OR(user1=me,user2=me). WHY a join table (EventAttendee) not an array:
    attendance carries state (status/ticket/dates) + needs a unique constraint.
  META: these are deliberate "good-enough-for-a-solo-MVP" choices — traded
    scale-hardening for shipping speed, with a known upgrade path for each.

C3) NOTABLE CHALLENGES & FIXES  ("walk me through a hard bug" material)
-----------------------------------------------------------------

C4) SCALING & PERFORMANCE  (bottlenecks in priority order; symptom -> fix)
-----------------------------------------------------------------
Framing: single-region monolith on pooled Postgres; attack order = feed,
  realtime, rate limiter, DB N+1.
  1 FEED/RANKING: scores 50 date-paginated rows in memory (can't rank
    globally; recomputes Haversine each request). Fix path: filter past +
    rank before paginate -> PostGIS + GIST spatial index -> precompute slow
    signals -> search engine (ES/Typesense) -> short-TTL per-user cache.
  2 REALTIME: globalThis, one process -> cross-instance emits fail. Fix:
    dedicated socket service + @socket.io/redis-adapter + authed handshake;
    or a managed provider (Ably/Pusher).
  3 RATE LIMITER: per-instance Map -> N× effective limit. Fix: Redis INCR+TTL;
    trusted client-IP.
  4 DATABASE: pooling already right (PgBouncer + DIRECT_URL). N+1/over-fetch —
    some list endpoints include full user rows + per-item findFirst (contacts
    sync, suggestions); fix with select, `in` batching, Sets over
    Array.includes; add composite indexes (events visibility+eventDate,
    attendees eventId, messages connectionId+sentAt, connections
    user1/user2+status); read replicas if reads dominate.
  5 DISPATCH: non-atomic claim (double-send) + 200 cap. Fix: atomic claim
    (UPDATE … WHERE sentAt IS NULL RETURNING), loop to drain, real queue.
  6 MEDIA/CLIENT: Supabase CDN fronts images; badge/bell poll 30s per mount
    -> SWR/socket push; runtime @import fonts -> next/font.
  ALREADY RIGHT: stateless routes scale horizontally; pooled DB; JWT edge auth;
    denormalized counter; feed pagination exists.
